## 1 · The shape

- **The HUB (you):** reads the GOAL and the code, cuts the work into units, lanes and tracks, writes the plan and the kickoff prompts, writes the tooling, cuts the base, grants the slots, merges every READY lane into the trunk one at a time, runs the gates on the merged tree, pushes the trunk, keeps the board, runs the quiet window, tags, writes the hand-off note, files the owner's answers. You never build a unit and never edit a lane's branch.
- **The build chats (Opus 5.5, one per track, started with `claude --model claude-opus-5-5 --name <TRACK>`):** each owns three to six lanes; scouts, builds, checks and reviews them as workflows with sub-agents; says READY per lane on its status file; never merges into or pushes the trunk; never touches another chat's lane. Their prompt's first word is `ultracode`, which switches on the Workflow tool.
- **The sub-agents: five agent types you write into `.claude/agents/<name>.md`** (frontmatter `model`, `effort`, `maxTurns`, and `tools` for the read-only ones; then the role text: the step budget, batch the reads, search before reading, no whole file over 20 KB, gates through the scripts, the hand-off note of section 3): `scout` (sonnet, low, 60 turns; Read, Grep, Glob, Bash, Write; writes the brief, never edits code, never runs a database command), `lane-builder` (opus, high, 80), `lane-builder-flagged` (opus, xhigh, 80: for a lane touching tenancy, access control, money, or anything whose bug is expensive), `lane-checker` (opus, medium, 80; read-only tools), `lane-reviewer` (opus, max, 80; read-only). Effort follows the stage: low where the work is mechanical, highest where a missed error costs most. The checker never fixes what it checks.
- **The owner:** answers in one line each, opens the terminals, keeps the machine awake, walks the result. Decisions are read, not made: a ruling that looks wrong for what the code shows is a question with a default, never a design choice of yours.
- **The cut.** A unit is one change with its files, its acceptance and an estimate in hours (at most about eight). A lane is two to six units in one territory, on one branch `build/<lane>` in one worktree `<wt>/<lane>`. A track is three to six lanes, one build chat. Tier 1 is the chain that makes the product usable end to end; tier 2 is the depth. Build chats: the lanes divided by five, rounded up, one to six. Slots (lanes running at once): from free memory (about 1.5 GB per worktree plus the project's test footprint; grant nothing under 4 GB free and pause the newest lane under it) and, when the project has a database, one database per lane and a non-overlapping block of migration ids per lane.

## 3 · How a lane is built

1. **Scouts first, all at once, in the track's first hour:** one `scout` per lane reads the files the units name and writes the brief and the contract. A brief is complete when a builder who has read only the contracts and the brief can build without asking. The chat asks for its slots (`SLOTS-ASKED:`).
2. **A granted lane:** the chat cuts the worktree from `BASE` with the cut script (`git worktree add -b build/<lane> <wt>/<lane> <BASE>`, the lane's env and database names, the install; it refuses an existing path or branch and never deletes), then launches the lane workflow: `Workflow({scriptPath: '<docs>/tracks/HUB/workflows/lane.js', args})` with lane, chat, repo, units, batches, base, slot, flagged, session and now, plus start, sliceRun, done, priorNote, diffFrom or dryRun as the run needs. Builders run one per batch in order, each a fresh agent given the brief, the previous hand-off note and its batch, nothing more; it commits as it goes, at least every 45 minutes, the unit in the message. The checker reads `git diff <base>...HEAD` and the brief, runs the gates through the scripts and returns PASS or FIX by name against the baselines; a FIX is built one effort level up and re-checked once. A flagged lane gets two reviewers at its end (contracts and tests; abuse and domain errors); findings are fixed once and re-checked once by the finder. The report, under 20 KB, with the evidence by path.
3. **The slice rule:** the first batch is one unit, the one the chain needs most. When it is committed and the lane's gates are green on the branch, the chat writes `LANE: <lane> READY-SLICE <tip>`; you merge it like a lane; the lane continues on its branch (no rebase; its later commits merge at the next READY). So the trunk carries real work within hours of the start, and a day that ends early still ships something.
4. **A finished lane:** `LANE: <lane> READY <tip>`. A red you send back (a new failure by name on the merged tree, a territory breach) is fixed on the branch within the hour it is read, before any new unit; two rounds at most, then the lane leaves the tag and its units move to the next one. The chain's lanes are the exception: they are fixed, because the chain needs them.
5. **Gates by name.** The baseline first. A lane is green when nothing that was green on the base is red on the branch, judged by failure name, never by count or exit code. Every typecheck and suite goes through a lock taken in arrival order (one per repository), scoped to the files the lane touched; never the full suite on a lane; the full suites run once, in the quiet window, by you.
6. **A question is a default plus a line,** never a wait: the builder builds the recorded default and says so in the report; the chat writes the question to its outbox; you put it on the board with the time the default applies.
7. **The hand-off note** is a builder's only output and the next builder's only input: `done:` the units with their SHAs; `in flight:` what is half done and where; `next:` the units left and the first step for each; `files touched:`; `the one thing to know:`; `evidence:` the log paths that prove the gates.
8. **Workflow facts that bit us:** the script must live under this folder (a path elsewhere is refused) with LF endings and no clock, filesystem or random call inside (the stamp comes in as `args.now`); a workflow agent cannot wait more than about ten minutes in a lock queue (the harness forces its return), so long gates run detached and are awaited; every workflow result lands in the chat's context, so returns stay under a few KB; never message a running workflow's agent by id (it resumes it as a second run): put rules in the args, or stop and relaunch with `done`; `resumeFromRunId` works in the same session only.

## 4 · How you merge

- One lane at a time per repository, READY-SLICE and READY alike, always the tip the status file names (branches move on within minutes). The steps are a script (`merge_lane.py prepare | conflicts | guards | commit | status | abort | finish`) so no agent improvises git: the territory check (the lane changed only its own files or the shared append points); an integration branch `int/<lane>-<tip7>` from the trunk; `git merge --no-ff --no-commit build/<lane>`; every hunk read; append conflicts resolved by keeping both regions, anything else back to the lane; the typecheck, the lane's suites and the guard checks on the merged tree (when the day is short, the typecheck only here and the lint once in the quiet window); the commit; `finish --push`, your own step: the trunk fast-forwarded and pushed; `BASE:` updated, a `MERGED:` line, a "from the HUB" note on the lane's status file; the next queued lane launched. Thirty to ninety minutes each; both repositories in parallel. A lane's worktree and databases go when the remote shows the merge and the lane is done.
- Never hand over with a gate script running (a detached script dies with the session on Windows); a fresh HUB restarts it first thing.

## 5 · Fresh chats, the context rule, the limits

- **The context rule:** over 250,000 tokens plan your hand-over; over 300,000, at the next safe point (nothing of yours running, no merge or lane half done), write the run record's "Resume here" and your status file with `STATE: RESTART` and `UPDATED` from `date`, then stop. No new work after the hand-over. A fresh chat starts from its kickoff prompt plus the resume line `resume: read your status file and your RUN-RECORD.md, then continue from the last finished step`; it never relaunches a running lane: it reads the run's journal and waits for the notification. Main chats keep their full window: never set `autoCompactWindow`.
- **`tools/context_now.py`:** a chat cannot see its own context, so this prints every chat's: the last request's usage (input + cache read + cache write) from the tail of each session transcript under the Claude Code projects folder for this directory (`~/.claude*/projects/<this folder's key>/<session>.jsonl`, never the sub-agents'), with the chat's name from `tools/token_roles.json`, largest first, RESTART over 300,000, "soon" over 250,000.
- **`tools/hook_context_restart.py`** (PostToolUse and Stop): over 250,000 tells the chat "soon" once; over 300,000 "now" every 25 tool calls; refuses a Stop once per session while over 300,000 and the status file does not yet say RESTART or HANDOVER; fails open; never for a sub-agent. The owner adds the two rows to `.claude/settings.json` (you never edit the settings file) and the top-level line `"subagentPromptCacheTtl": "1h"` (without it a sub-agent's cache expires in five minutes and every longer wait re-writes its whole context).
- **`tools/fresh_chat_launcher.py --loop`,** a plain background process of the owner's logon (never a scheduled task: a task kills its children when it ends), one check every two minutes: it reads every status file, `claude agents --json` and the transcripts' heads and tails, and decides per track: HAND-OVER (STATE RESTART or HANDOVER and no chat of the track stepped after its UPDATED time) means a launch now; NO CHAT (no live session of the track, the track not at a stop such as READY with every lane merged, PAUSED, STOPPED, COMPLETE or WAITING-OWNER, and no step for 30 minutes) means a launch with the resume line; the build tracks launch only once your `BASE-READY:` line exists. A launch is, in this folder, `claude --bg --name "<TRACK> <time>" --model <the track's model> "<the track's fenced block from KICKOFF-PROMPTS.md>` followed by the resume line; at most one per track per 45 minutes; a launched chat with no step after 15 minutes is noted (the usage limit, most likely) and after 45 minutes stopped and tried again; once the fresh chat has stepped, the launcher stops its own previous session of that track; the owner's interactive windows are never stopped. Commands: `--status`, `--once --dry-run`, `--pause "<why>"` and `--resume` (you pause it at the close), `--pause-track` and `--resume-track`, `--start`, `--stop`, `--restart`, `--launch-missing` (after a machine restart), `--self-test`; state and log under `%LOCALAPPDATA%\<project>-hub\launcher\`. You write it and test it; you never start or install it: you give the owner the `!` line.
- A background chat (`claude --bg`) may be refused Write and Edit in the shared repository (the isolation guard, unless the owner sets `bgIsolation` to none): it writes the hub files through Bash and small Python scripts; the worktrees are not affected.
- **The usage limit:** no API key. When a limit stops a chat, nothing is lost: the state is in the files and in git; the chat retries every 45 minutes with the resume line; the launcher restarts it. After any interruption: read the branch tips and each worktree's `git status` first; resume, never restart.
- **The context diet,** because cost is steps times context: 80 tool steps per agent (a builder stops at two or three units or 70 steps and writes its note); independent reads, searches and checks in one step; search before reading, read line ranges, no whole file over 20 KB, a file read once is not read again; scripts that print names and counts, the logs on disk cited by path; briefs under 15 KB, reports under 20 KB; registers over 30 KB through a tail or a search; think the next steps in one thought, then act; the hand-off note before any long stretch, not only at the stop. A main chat whose workflow results are large plans its hand-over at about 230,000.

## 6 · The rules that bind every chat

1. Nobody but the HUB moves or pushes the trunk; a build chat merges nothing into it.
2. A slot before a lane. A lane is cut from `BASE` on the board, never from the development branch, never from another lane; a lane that needs unmerged work builds on the contract and switches to the real code when the board shows the merge.
3. Tier 1 before tier 2, always; a tier 2 unit starts only when no tier 1 lane waits for a slot.
4. Territory: a lane touches only its own files; shared files are append-only under the banner `// -- <program> --` in the file's comment syntax, at the listed append points; a file that is not yours is changed by asking its owner through your outbox.
5. No new failure by name. Two reviewers on every flagged lane before its merge. Reports under 20 KB, evidence by path. Honest reports: green only when the exit code or the failure names were read; "fixed" only with a SHA; say what you verified and what you assumed.
6. Commits at least every 45 minutes, the unit in the message; the message from a file, ending with the session's trailers; by explicit path, never `git add -A` (another chat's half-written file gets swept in); the hub committed as you go; pushed only by the HUB on the owner's word.
7. Never force-push, rebase a pushed branch, stash, or check out over uncommitted work; never delete a branch or a worktree before the remote shows its tip; never touch what the GOAL protects.
8. Time stamps from `date` or the commit time, never estimated.
9. No secret in a repository, a prompt or a chat.
10. The owner's word is needed for: a hub push; starting or installing the launcher or any persistence (the `!` lines go to the owner); any settings file; a deploy; stopping a container; a live database or client data; anything outside the program's own branches; a deletion the rules do not already allow. The tag at the green needs no word when the GOAL says so.
11. Questions to the owner: a default plus a line on the board; batched, each with the time its default applies; a decision document in five parts (the problem in plain words, the long-term solution, the options, the recommendation, a one-line reply to copy back). A note to an outside party: explanation, reason, long-term impact, options, recommendation, in a friendly tone. A ruling is recorded where the chats read it, with its stamp and the owner's words, before anyone acts on it.

# 5 · The cases, one by one

| What happened | What already protects you | What to do |
|---|---|---|
| A chat hit the usage limit | Nothing is lost: the state is in the files and in git. The chat retries every 45 minutes; the launcher relaunches a silent track after 30 minutes, with the resume line. | Wait, or paste the recovery prompt to see where everything stands. |
| A chat's context filled | It wrote its "Resume here" and `STATE: RESTART`; the launcher starts a fresh chat of that track within two minutes. | Nothing. Check the board when convenient. |
| You closed a window or a background chat died | NO CHAT for 30 minutes → the launcher relaunches it with the resume line; a fresh chat never relaunches a live workflow run, and relaunches a dead one with `done` and `priorNote`. | Nothing, or `--launch-missing` (the recovery prompt gives the exact line) to skip the 30-minute wait. |
| The HUB chat is gone | Same as above: the HUB is a track the launcher knows (Prompt 0). | Same. |
| The machine restarted | Worktrees, branches and files are on disk; the launcher is a plain process and is **not** running after a restart. | Open a terminal in `C:\Users\ruchi\1-addic`, start the launcher loop with its `!` line from section 4 step 3, then `--launch-missing`. |
| The launcher loop died | `--status` says NOT RUNNING. | Its `--start` line (section 4 step 3). |
| A lane's workflow run died with its session | The run record names the run; the branch holds every commit; the progress file holds the units. | The fresh chat of that track relaunches the lane with `done` and `priorNote`; the recovery prompt reports it. |
| A merge was half done | `merge_lane.py` works on an integration branch `int/<lane>-<tip7>`; the trunk moves only at `finish`. | The fresh HUB runs `merge_lane.py status`, then `abort` or continues. |
| Chrome or Node missing on a fresh machine | The browser tests need Google Chrome (`channel: 'chrome'`) and Node 22. | Install them; the gates say which is missing by name. |
